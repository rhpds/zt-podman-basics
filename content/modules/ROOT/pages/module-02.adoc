= Working with a Container Registry

A container image is a stack of compressed filesystem snapshots bundled with metadata that describes how to run them.

A registry stores and serves images as a name and tag associated with a hash value.
The image reference you use to pull from or push to a registry is made up of three parts.

image::image-ref.png[UBI 10 OCI reference]

First is the name of the registry.
We'll see how this works during this part of the lab.

Next is what's called the 'repository' that many just refer to as the name.
In reality, this can include a lot of different information depending on the type and configuration of the registry.
For example, the Red Hat `registry.access.redhat.com` registry groups UBI images by version as part of the repository information, where `quay.io` might include username or organization name in addition to the name of the image.

Finally comes the tag, which allows for identifying certain versions of images.

== Registry Types

Registries come in a few varieties:

* **Public registries** — these allow for anonymous pulls of published images, like some images in `quay.io` or `docker.io`
* **Private registries** — access-controlled, used in production and air-gapped environments like Artifactory or Red Hat Satellite

In addition to these sorts of full featured sites, you can run a simple registry for local usage.
This lab uses a **local registry** running on this system.
It uses SSL but requires no authentication.

For this lab, the registry hostname is stored in the `REGISTRY` environment variable for convenience.

== Search the Registry

You can use `podman` to find images without needing to visit a website.
The built in `search` command can look for images that contain a specific name in any registry that supports search.

[source,bash,role=execute]
----
podman search ${REGISTRY}/
----

[source,text]
----
NAME                               DESCRIPTION
registry-xxx.example.com/hostinfo-app
----

The local registry acts differently than a production registry and the filtering is done by `podman`. 
When searching in one of these, a `search` like this will probably fail, and how substrings are handled depends on the particular registry.

For example, *quay.io* searches the namespaces as well as metadata, so there may be more results than you might originally expect.

[source,bash,role=execute]
----
podman search --limit 10 quay.io/fedora/fedora
----

[source,text]
----
NAME                               DESCRIPTION
quay.io/fedora/fedora                  
quay.io/fedora/fedora-coreos           
quay.io/fedora/fedora-bootc

The `search` subcommand has a number of useful ways to both limit results and add information to the results.

== Inspect Before You Pull

Before downloading an image, you might want to find out more information about it than what was returned in search.
Another container tool useful for dealing with remote images and registries is `skopeo`.
You can use `skopeo` to read image metadata directly from the registry.

[source,bash,role=execute]
----
skopeo inspect docker://${REGISTRY}/hostinfo-app | grep -A7 '"Env"'
----

[source,text]
----
    "Env": [
        "HOME=/tmp",
        "CONTAINER_DEFAULT_USER=65532",
        "PYTHON_VERSION=3.11.15",
        "PYTHONDONTWRITEBYTECODE=1",
        "PYTHONUNBUFFERED=1",
        "PATH=/app/venv/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
    ],
----

The grep shows us just the section of the metadata that defines the environment variables set in the image.
Before pulling, you already know:

* The container will run as UID 65532 — not root
* It's a Python 3.11 runtime
* The application likely lives in `/app/venv`, which is a non-standard addition to the PATH

This is part of the metadata bundled with the image.
Skopeo reads it straight from the registry API, which makes it useful for auditing images before pulling them in automated pipelines or air-gapped environments where you want to verify before committing to a download.

== Pull the Image

To run a container, you first need to have the image available locally.
You can have `podman` download it as part of starting it, but we'll use the `pull` command to download it first.

[source,bash,role=execute]
----
podman pull ${REGISTRY}/hostinfo-app
----

[source,text]
----
Trying to pull registry-xxx.example.com/hostinfo-app:latest...
Getting image source signatures
Copying blob a1b2c3d4e5f6 done   |
Copying blob 7890abcdef12 done   |
Copying blob fedcba098765 done   |
...
Writing manifest to image destination
registry-xxx.example.com/hostinfo-app:latest
----

Each `Copying blob` line is a layer, a compressed filesystem tarball being fetched.
Layers are identified by their digest, which means if you already have a layer from a prior pull, `podman` skips it.
Pulling a second image built on the same base is much faster because the shared base layers already exist.

Local operations like tagging and retagging leave that hash unchanged.
Registry operations like push and pull can produce a different digest even for identical content.

== Examine the Layers

Like `skopeo`, `podman` can tell you a lot about an image you've downloaded.
The `history` command will give you layer by layer information about how an image was built.

[source,bash,role=execute]
----
podman history ${REGISTRY}/hostinfo-app | head -15
----

----

You can see in the output where the application was installed on the base image.
In the COMMENT column, the word `FROM` shows you the hash of the previous starting point.
Notice that one of them is an OCI reference, not a hash.
Everything from that line upward is work done to build the application.
Below that line are layers created by Red Hat to create the base.

Each row is one filesystem snapshot stacked on the previous, generated as the output of the command listed.
The final image is all of them in order, read-only.
When you run a container, a thin writable layer is added on top but the image layers themselves never change.

== Names Are Metadata

The IMAGE ID is derived from the content of the image, it's a hash of the layer digests.
For local operations like tagging and retagging, the IMAGE ID stays the same because that content isn't changed.
You can add names, remove names, and the underlying layers don't move.

You already saw `ubi9` is in local storage.

[source,bash,role=execute]
----
podman images
----

[source,text]
----
REPOSITORY                             TAG      IMAGE ID      CREATED       SIZE
registry.access.redhat.com/ubi9/ubi   latest   a1b2c3d4e5f6  3 weeks ago   212 MB
${REGISTRY}/hostinfo-app              latest   7890abcdef12  2 weeks ago   245 MB
----

The REPOSITORY column has the full pattern of registry and repository listed, followed by the tag in the TAG column.
Look at its IMAGE ID.

If we wanted to copy this image into our local registry, we need to update the repository name to include our registry.

We can do this with `podman tag`

[source,bash,role=execute]
----
podman tag registry.access.redhat.com/ubi9/ubi ${REGISTRY}/ubi9
----

[source,bash,role=execute]
----
podman images
----

[source,text]
----
REPOSITORY                             TAG      IMAGE ID      CREATED       SIZE
registry.access.redhat.com/ubi9/ubi   latest   a1b2c3d4e5f6  3 weeks ago   212 MB
${REGISTRY}/ubi9                       latest   a1b2c3d4e5f6  3 weeks ago   212 MB
${REGISTRY}/hostinfo-app              latest   7890abcdef12  2 weeks ago   245 MB
----

Notice the new repository reference but the IMAGE IDs are the same.
We haven't done anything that modifies the image, just the metadata.

Now push it to the local registry.

[source,bash,role=execute]
----
podman push ${REGISTRY}/ubi9
----
....
Checking if image destination supports signatures
Error: Copying this image would require changing layer representation, which we cannot do: "Would invalidate signatures"
....

Since this is an official Red Hat image, it has a digital signature to prove its validity.
Working with signatures is part of another lab, so for this lab, we're going to remove it when pushing our copy to the local registry.

[source,bash,role=execute]
----
podman push --remove-signatures ${REGISTRY}/ubi9
----
....
Copying blob b38850413dc5 done   | 
Copying config b90f3ea6a3 done   | 
Writing manifest to image destination
....

Verify our new copy is in the registry alongside `hostinfo-app`:

[source,bash,role=execute]
----
podman search ${REGISTRY}/
----

This process of copying an image from one registry to another is known as mirroring.
It's a common way to reduce the dependency on a remote service during build, maintain a known set of available images, and more.

With our copy available to the local network, we don't need to keep the local copy.
Use `podman rmi` to remove an image reference from local storage.

[source,bash,role=execute]
----
podman rmi registry.access.redhat.com/ubi9/ubi
----

[source,text]
----
Untagged: registry.access.redhat.com/ubi9/ubi:latest
----

Notice the output was **Untagged**, not **Deleted**.
The image is still present because `${REGISTRY}/ubi9` still references the ID.
A name is a pointer, removing the pointer doesn't remove what it pointed at.

[source,bash,role=execute]
----
podman images
----

[source,text]
----
REPOSITORY             TAG      IMAGE ID      CREATED       SIZE
${REGISTRY}/ubi9       latest   a1b2c3d4e5f6  3 weeks ago   212 MB
${REGISTRY}/hostinfo-app  latest  7890abcdef12  2 weeks ago   245 MB
----

== What the Image Declares

`skopeo` showed you the runtime environment before the pull. Now check what the image declares about how it expects to be run:

[source,bash,role=execute]
----
podman inspect ${REGISTRY}/hostinfo-app | grep -A2 ExposedPorts
----

[source,text]
----
        "ExposedPorts": {
            "8000/tcp": {}
        },
----

The image declares it expects to be reachable on port 8000.
This is metadata set by the image author but it's not enforced automatically.
You'll need this when you map container ports to the host.

In the next module you'll run this `hostinfo-app` image as a container and see what sort of isolation happens in practice.
