= Working with a Container Registry

A container image is a stack of compressed filesystem snapshots bundled with metadata that describes how to run them. A registry stores and serves those bundles — you refer to them by name, but what you're actually getting is addressed by a content hash. Local operations like tagging and retagging leave that hash unchanged. Registry operations like push and pull can produce a different digest even for identical content.

== Registry Types

Registries come in a few varieties:

* **Public registries** — open to anyone: `docker.io`, `ghcr.io`, `quay.io`, `registry.access.redhat.com`
* **Private enterprise registries** — access-controlled, used in production and air-gapped environments
* **Local registries** — running on the same network or machine, for development, testing, and disconnected environments

This lab uses a **local registry** running on this system. The registry hostname is stored in the `REGISTRY` environment variable. It uses SSL and requires no authentication.

== Search the Registry

Discover what images are available:

[source,bash,role=execute]
----
podman search ${REGISTRY}/
----

[source,text]
----
NAME                               DESCRIPTION
registry-xxx.example.com/hostinfo-app
----

One image is available. You'll add a second later in this module.

== Inspect Before You Pull

Before downloading an image, use `skopeo` to read its metadata directly from the registry — without pulling a single byte.

[source,bash,role=execute]
----
skopeo inspect docker://${REGISTRY}/hostinfo-app | grep -A7 '"Env"'
----

[source,text]
----
    "Env": [
        "HOME=/tmp",
        "CONTAINER_DEFAULT_USER=65532",
        "PYTHON_VERSION=3.11.15",
        "PYTHONDONTWRITEBYTECODE=1",
        "PYTHONUNBUFFERED=1",
        "PATH=/app/venv/bin:/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin"
    ],
----

Before pulling, you already know:

* The container will run as UID 65532 — not root
* It's a Python 3.11 runtime
* The application lives in `/app/venv`, which is first on the PATH

This is part of the metadata bundled with the image. Skopeo reads it straight from the registry API, which makes it useful for auditing images before pulling them in automated pipelines or air-gapped environments where you want to verify before committing to a download.

== Pull the Image

[source,bash,role=execute]
----
podman pull ${REGISTRY}/hostinfo-app
----

[source,text]
----
Trying to pull registry-xxx.example.com/hostinfo-app:latest...
Getting image source signatures
Copying blob a1b2c3d4e5f6 done   |
Copying blob 7890abcdef12 done   |
Copying blob fedcba098765 done   |
...
Writing manifest to image destination
registry-xxx.example.com/hostinfo-app:latest
----

Each `Copying blob` line is a layer — a compressed filesystem tarball being fetched. Layers are identified by their digest, which means if you already have a layer from a prior pull, Podman skips it. Pulling a second image built on the same base is much faster because the shared base layers are already local.

== Examine the Layers

[source,bash,role=execute]
----
podman history ${REGISTRY}/hostinfo-app
----

[source,text]
----
ID            CREATED        CREATED BY                                     SIZE
a1b2c3d4e5f6  8 weeks ago    /bin/sh -c #(nop) CMD ["/app/venv/bin/gu...  0 B
<missing>     8 weeks ago    /bin/sh -c #(nop) COPY dir:a1b2 in /app/      7.1 kB
<missing>     8 weeks ago    /bin/sh -c pip install --no-cache-dir -r ...   45.2 MB
<missing>     8 weeks ago    /bin/sh -c #(nop) WORKDIR /app                 0 B
<missing>     2 months ago   /bin/sh -c dnf install -y python3.11 ...       312 MB
...
----

The output is long — this image has over 30 layers. The `<missing>` image ID is normal for pulled images: intermediate layer IDs aren't stored locally, only the final image's ID. What you can read is the CREATED BY column — it shows the instruction that produced each layer. The top rows are application steps: the default command set, files copied in, packages installed. Further down are the base image layers: the Python runtime, OS packages, system libraries.

Each row is one filesystem snapshot stacked on the previous. The final image is all of them in order, read-only. When you run a container, a thin writable layer is added on top — but the image layers themselves never change.

== Names Are Metadata

The IMAGE ID is derived from the content of the image — it's a hash of the layer digests. For local operations like tagging and retagging, the IMAGE ID stays the same because the content hasn't changed. You can add names, remove names, and the underlying layers don't move.

`ubi9` is already in local storage from lab setup. Look at its IMAGE ID:

[source,bash,role=execute]
----
podman images
----

[source,text]
----
REPOSITORY                             TAG      IMAGE ID      CREATED       SIZE
registry.access.redhat.com/ubi9/ubi   latest   a1b2c3d4e5f6  3 weeks ago   212 MB
${REGISTRY}/hostinfo-app              latest   7890abcdef12  2 weeks ago   245 MB
----

Add a new name pointing to the same content — a reference for the local registry:

[source,bash,role=execute]
----
podman tag registry.access.redhat.com/ubi9/ubi ${REGISTRY}/ubi9
----

[source,bash,role=execute]
----
podman images
----

[source,text]
----
REPOSITORY                             TAG      IMAGE ID      CREATED       SIZE
registry.access.redhat.com/ubi9/ubi   latest   a1b2c3d4e5f6  3 weeks ago   212 MB
${REGISTRY}/ubi9                       latest   a1b2c3d4e5f6  3 weeks ago   212 MB
${REGISTRY}/hostinfo-app              latest   7890abcdef12  2 weeks ago   245 MB
----

Same IMAGE ID — `podman tag` added a name, not a copy. Push it to the local registry:

[source,bash,role=execute]
----
podman push ${REGISTRY}/ubi9
----

Verify it's in the registry alongside `hostinfo-app`:

[source,bash,role=execute]
----
podman search ${REGISTRY}/
----

Now remove the original public registry reference:

[source,bash,role=execute]
----
podman rmi registry.access.redhat.com/ubi9/ubi
----

[source,text]
----
Untagged: registry.access.redhat.com/ubi9/ubi:latest
----

**Untagged**, not **Deleted**. The content is still present because `${REGISTRY}/ubi9` still references it. A name is a pointer to content — removing the pointer doesn't remove what it pointed at.

[source,bash,role=execute]
----
podman images
----

[source,text]
----
REPOSITORY             TAG      IMAGE ID      CREATED       SIZE
${REGISTRY}/ubi9       latest   a1b2c3d4e5f6  3 weeks ago   212 MB
${REGISTRY}/hostinfo-app  latest  7890abcdef12  2 weeks ago   245 MB
----

Same IMAGE ID. The content never moved.

== What the Image Declares

`skopeo` showed you the runtime environment before the pull. Now check what the image declares about how it expects to be run:

[source,bash,role=execute]
----
podman inspect ${REGISTRY}/hostinfo-app | grep -A2 ExposedPorts
----

[source,text]
----
        "ExposedPorts": {
            "8000/tcp": {}
        },
----

The image declares it expects to be reachable on port 8000. This is metadata set by the image author — it's not enforced automatically, but it's the contract the image publishes. You'll need this when you map container ports to the host.
