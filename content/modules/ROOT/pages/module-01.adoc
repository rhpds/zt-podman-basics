= Podman Fundamentals

Podman is an OCI-compliant, daemonless container engine for developing, managing, and running containers on Linux. Unlike Docker, Podman has no central daemon — each container runs as a child process of the command that started it.

Podman is Docker CLI-compatible, meaning the vast majority of `docker` commands work as `podman` commands with no changes. It also supports both rootless mode (containers running as a regular user) and rootful mode (containers running as root), giving you flexibility in how you manage privilege.

In this lab you are working as root, which is the pattern for the ZeroTouch labs environment.

== Verify the Podman Installation

Start by confirming what version of Podman is installed on this system.

[source,bash,role=execute]
----
podman --version
----

You should see output like this:

[source,text]
----
podman version 5.x.x
----

Podman 5.x is the current major version on RHEL 10. The version string follows `major.minor.patch` — expect at least version 5 here.

== List Available Images

The local image cache is where Podman stores images you have pulled. Let's see what's there.

[source,bash,role=execute]
----
podman images
----

You should see one image already present:

[source,text]
----
REPOSITORY                             TAG         IMAGE ID      CREATED       SIZE
registry.access.redhat.com/ubi9/ubi   latest      a1b2c3d4e5f6  3 weeks ago   212 MB
----

This image was pulled during lab setup and will be used in the next module. The columns here tell you:

* **REPOSITORY** — where the image came from (registry path and name)
* **TAG** — version label on the image
* **IMAGE ID** — content-addressed hash (first 12 characters)
* **CREATED** — when the image was built
* **SIZE** — uncompressed size on disk

== Check Running Containers

Podman tracks containers separately from images. Let's see what's running.

[source,bash,role=execute]
----
podman ps
----

And all containers, including stopped ones:

[source,bash,role=execute]
----
podman ps -a
----

Both commands should return an empty list. No containers have been started yet. The `-a` flag is the one you'll reach for most often when debugging — it shows everything, not just what's actively running.

The `ps` columns are:

* **CONTAINER ID** — unique identifier for the container instance
* **IMAGE** — which image this container was created from
* **COMMAND** — what command the container is running
* **CREATED** — when the container was started
* **STATUS** — current state: `Up`, `Exited`, `Paused`
* **PORTS** — published port mappings
* **NAMES** — human-readable name (auto-assigned or you set it with `--name`)

== Images vs Containers

Before moving on, a key conceptual distinction:

* An **image** is a read-only template — a blueprint. It contains the filesystem layers, configuration, and metadata that define what a container will look like when it starts.
* A **container** is a running instance created from an image. It has its own writable layer on top of the read-only image layers.

If you think in object-oriented terms: the image is the class, the container is the object.

[NOTE]
====
You can run many containers from the same image simultaneously. Each container gets its own writable layer but shares the underlying read-only image layers. This is what makes containers lightweight compared to virtual machines.
====
