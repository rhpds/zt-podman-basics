= Interactive Containers

A container gives an application its own view of the system — its own filesystem, users, and processes — while sharing the host's kernel. In this module you'll explore that isolation from inside a running container, then observe the same container from the host.

== Run a Container Interactively

Launch a shell inside the `hostinfo-app` container:

[source,bash,role=execute]
----
podman run -it --rm ${REGISTRY}/hostinfo-app /bin/bash
----

Your prompt changes to something like `root@a1b2c3d4e5f6:/#` — you're inside the container. The flags:

* `-i` — interactive: keep STDIN open so you can type commands
* `-t` — allocate a pseudo-TTY so you get a proper shell prompt
* `--rm` — remove the container when it exits
* `/bin/bash` — override the default CMD; run bash instead of the application

== The Application Environment

The container exists to run `hostinfo-app`. Its files are at `/app`:

[source,bash,role=execute]
----
ls /app
----

[source,bash,role=execute]
----
cat /app/config.json
----

This is the application's configuration. It's part of the image — present every time a container starts from this image.

== Filesystem Scope

[source,bash,role=execute]
----
df -hP
----

The root filesystem is an overlay — the image layers stacked together with a thin writable layer on top. Directories like `/var` and `/home` exist within that overlay as empty directories. They're not connected to the host's `/var` or `/home` — those paths and their contents are not visible here.

The only host filesystem paths that cross into the container are the three network configuration files the runtime injects automatically:

[source,bash,role=execute]
----
grep '/etc/' /proc/mounts
----

[source,text]
----
/dev/sdX /etc/hostname ext4 ro,...
/dev/sdX /etc/hosts ext4 ro,...
/dev/sdX /etc/resolv.conf ext4 ro,...
----

Everything else in the container's filesystem is the image's content.

== User Context

[source,bash,role=execute]
----
id
----

The container runs as UID 65532 — a non-root user with no special privileges. On the host you are running as `rhel`, but the image drops to an even more restricted UID. The `hostinfo-app` image was built this way deliberately: the application doesn't need elevated privileges, and running without them limits what a compromised process could do.

== Process View

The container has its own PID namespace — it can only see processes within its own boundary. Check which PIDs are visible:

[source,bash,role=execute]
----
ls /proc | grep -E '^[0-9]+$'
----

Only a handful of PIDs are listed: the bash shell you're running and its parent processes. Every other process on the host — every service, daemon, and user session — is invisible. The container cannot see or signal anything outside its PID namespace.

== Shared Kernel

[source,bash,role=execute]
----
uname -r
----

Note this kernel version — you'll verify it against the host in a moment. A container doesn't run its own kernel — it shares the host kernel directly. The isolation you've seen (filesystem scope, user context, process view) is enforced by kernel namespaces and cgroups, not by a hypervisor. This is why containers start in milliseconds rather than seconds, and why they're not a complete security boundary on their own.

== The Host's View

Exit the container:

[source,bash,role=execute]
----
exit
----

From inside, the container looked like a self-contained environment. From the host, it's a process. Run the container in the background to observe it from the host side:

[source,bash,role=execute]
----
CID=$(podman run -d --name hostinfo-demo ${REGISTRY}/hostinfo-app)
echo $CID
----

* `-d` — detached: run in the background and return the container ID

The full container ID is captured in `$CID`. Like the name, the ID is a valid way to refer to a container in any Podman command — names are for human readability, IDs are how Podman and the kernel track containers internally. You'll use both interchangeably as you work with containers.

Confirm the kernel version matches what you saw inside the container:

[source,bash,role=execute]
----
uname -r
----

Same version — the container shared this kernel the entire time.

Find the command the container is running, then use it to locate the process on the host:

[source,bash,role=execute]
----
podman inspect $CID | grep -A6 '"Cmd"'
----

[source,text]
----
        "Cmd": [
            "/app/venv/bin/gunicorn",
            "--workers",
            "2",
            "--bind",
            "0.0.0.0:8000",
            "app:app"
        ],
----

[source,bash,role=execute]
----
ps aux | grep gunicorn
----

[source,text]
----
983035   68739  0.0  0.6  30812 24740 ?  Ss   11:58  0:00 /app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
983035   68741  0.0  0.8  41296 29812 ?  S    11:58  0:00 /app/venv/bin/python3 /app/venv/bin/gunicorn --workers 2 --bind 0.0.0.0:8000 app:app
----

The UID on the host is not 65532 — it's a number from a different range entirely. Rootless Podman uses user namespaces: container UIDs are mapped to a range of host UIDs allocated to the `rhel` user via `/etc/subuid`. Inside the container you see UID 65532; on the host the kernel sees the mapped UID. The isolation is real at the kernel level, not just in Podman's view.

`podman top` gives a container-aware view of the same processes — equivalent to running `ps aux` from inside the container, but read from the host:

[source,bash,role=execute]
----
podman top hostinfo-demo
----

[source,text]
----
USER        PID    PPID   %CPU  ELAPSED  TTY  TIME  COMMAND
65532       12345  12340  0.0   10s      ?    0s    /app/venv/bin/gunicorn hostinfo:app -w 2 -b 0.0.0.0:8000
65532       12346  12345  0.0   10s      ?    0s    /app/venv/bin/gunicorn hostinfo:app -w 2 -b 0.0.0.0:8000
----

`podman stats` shows live resource usage for a running container — useful for checking what a container is actually consuming:

[source,bash,role=execute]
----
podman stats --no-stream hostinfo-demo
----

[source,text]
----
ID            NAME           CPU %   MEM USAGE / LIMIT   MEM %   NET IO      BLOCK IO   PIDS
a1b2c3d4  hostinfo-demo  0.00%   8.5MB / 7.6GB       0.11%   656B / 0B   0B / 0B    3
----

The isolation you've been observing has a mechanism behind it. Rootless Podman containers are scoped to your user's cgroup tree. The cgroup scope name contains the container ID — use `$CID` to find it directly:

[source,bash,role=execute]
----
systemd-cgls --user --no-pager | grep -A4 $CID
----

[source,text]
----
  └─app.slice
    └─libpod-a1b2c3d4e5f6[...].scope
      └─container
        ├─12345 /app/venv/bin/gunicorn hostinfo:app -w 2 -b 0.0.0.0:8000
        └─12346 /app/venv/bin/gunicorn hostinfo:app -w 2 -b 0.0.0.0:8000
----

The same ID Podman returned when you started the container is in the cgroup scope name. The container has its own scope within your user's cgroup tree — this is where the kernel enforces the isolation you observed from inside: the separate process view, the resource accounting, the UID.

Clean up the background container:

[source,bash,role=execute]
----
podman rm -f hostinfo-demo
----

== What's Next

The isolation you've seen here is the default. A container gets its own filesystem, its own user context, its own process view — and the host doesn't cross those boundaries unless you explicitly allow it.

Running a real application means deciding which host resources it needs access to, and how to grant that access safely. Published ports, volume mounts, and environment variables are all ways of punching deliberate, controlled holes in the isolation boundary. That's where the work of deploying containerized applications begins.
